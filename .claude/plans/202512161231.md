基于你上传的代码文件（特别是 `workflow_orchestrator.py`, `workflow.py`, `checkpointer.py` 和 `pdf_parsing.py`），这个架构目前存在几个比较**显著的缺陷**，如果不解决，可能会导致代码难以维护、系统无法扩展或在生产环境中不稳定。

以下是针对该架构的详细批判分析：

### 1\. 致命缺陷：“双脑”架构 (Split-Brain Architecture)

这是最严重的问题。你的项目中同时存在两套完全独立的“工作流引擎”，它们做的事情几乎一模一样：

  * **引擎 A (LangGraph)**: 定义在 `app/graph/workflow.py` 中，使用 `StateGraph`，节点在 `app/graph/nodes/` 下。这是现代的、基于图的编排方式。
  * **引擎 B (Orchestrator)**: 定义在 `app/services/workflow_orchestrator.py` 中，使用 `WorkflowOrchestrator` 类，通过 `execute_full_workflow` 方法**线性地**调用各个步骤。

**问题所在**：

  * **逻辑重复**：`WorkflowOrchestrator` 中的 `_process_chunk_stage1`、`_merge_outlines` 等方法，与 `app/graph/nodes/` 下的节点逻辑高度重复。一旦你需要修改业务逻辑（比如改变 Prompt 策略），你需要同时修改两处代码，极易造成不一致。
  * **资源浪费**：如果你的 API 入口（`app/api/`）调用的是 Orchestrator，那么你精心设计的 LangGraph（包含错误处理路由、状态机管理）就完全没有被用到；反之亦然。
  * **建议**：**彻底删除 `WorkflowOrchestrator`**。将 Orchestrator 中的任何特有逻辑（如 Prompt 格式化、图片 token 处理）迁移到 LangGraph 的 Node 函数中，让 LangGraph 成为唯一的业务流驱动引擎。

### 2\. 持久化机制不可靠 (Persistence Issue)

在 `app/storage/checkpointer.py` 中，你的 Checkpointer 实现存在隐患：

```python
class WorkflowCheckpointer:
    def __init__(self, db_path="..."):
        # ...
        self._saver = MemorySaver()  # <--- 问题在这里
```

  * **问题所在**：
      * **内存易失性**：你使用了 `MemorySaver` 作为 LangGraph 的后端。这意味着图的执行状态（Graph State，即当前运行到哪个节点、线程历史等）仅保存在**内存**中。一旦服务器重启或崩溃，所有处于“等待人工审核 (`human_review`)”状态的任务，其**图上下文都会丢失**，导致无法恢复流程，即使用户在前端点击“继续”，系统也不知道该从图的哪里继续。
      * **JSON 存盘是“伪”持久化**：虽然你手写了 `_save_to_json` 把数据存到了磁盘，但这只是数据的快照，不是 LangGraph 的“执行栈”。LangGraph 需要知道的是 Stack Frame（执行栈帧）。
  * **建议**：替换 `MemorySaver` 为 **`SqliteSaver`** 或 **`PostgresSaver`**（来自 `langgraph.checkpoint.sqlite` 或 `langgraph.checkpoint.postgres`）。这样即使服务重启，LangGraph 也能从数据库加载执行栈，真正实现 Long-running Human-in-the-loop workflow。

### 3\. 并发性能瓶颈 (Blocking I/O)

虽然 `workflow_orchestrator.py` 和 API 层面使用了 `async/await`，但在底层 LLM 调用上存在阻塞：

  * **问题所在**：
      * 在之前的 `app/services/llm/provider.py` 中，`LLMClient` 使用了 `requests` 库（同步库）。
      * 在 `app/services/workflow_orchestrator.py` 中，虽然 `execute_full_workflow` 是 `async` 的，但它调用了 `call_model`（同步函数）。
      * **后果**：在 FastAPI 等异步框架中，调用同步阻塞的 HTTP 请求会**阻塞整个 Event Loop**。这意味着当一个用户正在等待 OpenAI 返回（可能需要几十秒）时，服务器将无法处理其他用户的任何请求（包括简单的健康检查），并发能力几乎退化为 1。
  * **建议**：将底层 LLM 客户端重构为使用 `httpx` (AsyncClient) 或 `aiohttp`，确保从底层的 HTTP 请求到上层的 Graph Node 全链路都是异步非阻塞的。

### 4\. 扩展性限制 (Local Filesystem Dependency)

  * **问题所在**：代码大量依赖本地文件系统路径：
      * `Path("data/intermediate") / task_id`
      * `self.db_path = Path(db_path)`
  * **后果**：这使得该应用变成了\*\*有状态（Stateful）\*\*应用。你无法将其部署在多副本（Replica）环境（如 K8s 的多个 Pod），因为请求打到 Pod A 生成的文件，Pod B 无法读取。这限制了系统的水平扩展能力。
  * **建议**：
      * 对于文件（PDF, Markdown, Images）：抽象一个 `FileStorage` 接口，支持 S3/MinIO/OSS 等对象存储。
      * 对于状态（JSON DB）：如前所述，迁移到真正的数据库（PostgreSQL/Redis）。

### 5\. 生产环境代码中混杂 Mock

  * **问题所在**：在 `app/services/workflow_orchestrator.py` 中：
    ```python
    async def _parse_with_mineru(self, pdf_path: str) -> str:
        # ...
        self.logger.log_summary("📄 [MinerU] PDF parsing not yet implemented, using mock data")
        return mock_markdown  # <--- 硬编码的 Mock
    ```
    而在 `app/graph/nodes/pdf_parsing.py` 中却似乎试图调用真实的 `MinerUClient`。
  * **后果**：这再次印证了“双脑架构”导致的代码分裂。开发者可能更新了 Graph 中的真实逻辑，却忘了 Orchestrator 还在用 Mock，导致测试行为与生产行为不一致。

### 总结修正路线图

1.  **Delete**: 删除 `app/services/workflow_orchestrator.py`，它是个累赘。
2.  **Refactor**: 确保 `app/graph/nodes/` 中的逻辑包含了 Orchestrator 里原本想实现的所有细节（如 Token 处理、Prompt 组装）。
3.  **Upgrade**: 将 `app/storage/checkpointer.py` 中的 `MemorySaver` 换成 `SqliteSaver`。
4.  **Fix**: 将 `app/services/llm/provider.py` 改写为异步 (`async/await` + `httpx`)。
