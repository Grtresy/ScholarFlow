# 第2章 系统架构总览

## 2.1 架构设计原则

### 2.1.1 设计理念

ScholarFlow 的架构设计遵循以下核心原则：

**1. 模块化与解耦**
- 每个功能模块职责单一，边界清晰
- 模块间通过明确定义的接口通信
- 支持独立开发和测试
- 便于替换和升级单个组件

**2. 可扩展性**
- 支持水平扩展，可处理更大规模的文档
- 插件化架构，易于添加新功能
- 可配置的工作流，支持自定义节点
- 多租户支持，为不同用户提供隔离环境

**3. 可恢复性**
- 状态持久化，支持断点续传
- 错误自动恢复，减少人工干预
- 完整的审计日志，便于问题追踪
- 数据备份和恢复机制

**4. 可观测性**
- 全链路日志记录
- 实时性能监控
- 错误分类和告警
- 详细的执行指标

**5. 生产就绪**
- 容器化部署，支持 Kubernetes
- 负载均衡和故障转移
- 安全加固和权限控制
- 资源限制和配额管理

### 2.1.2 架构风格

ScholarFlow 采用**分层架构 + 事件驱动架构**的组合模式：

**分层架构**:
- **表现层**: React 前端界面
- **接口层**: FastAPI REST API
- **业务层**: LangGraph 工作流引擎
- **服务层**: PDF 解析、LLM 处理、渲染服务
- **数据层**: SQLite + JSON 存储

**事件驱动**:
- 工作流节点通过事件传递状态
- 异步处理提升性能
- 支持事件订阅和通知
- 便于监控和调试

### 2.2.2 数据流概览

ScholarFlow 的端到端数据流如下：

```
PDF文件 → 上传 → LangGraph工作流 → 渲染 → 演示文稿
    ↓
 MinerU解析 → 文本分块 → LLM处理 → 合并大纲 → 人工审核 → Marp渲染
    ↓
 图片提取 → Token化 → 恢复图片 → 输出多格式文件
```

**详细流程**:
1. 用户上传 PDF 文件到 FastAPI 服务器
2. FastAPI 调用 LangGraph 工作流启动处理
3. MinerU 解析 PDF，提取 Markdown 和图片
4. 文本分块器将内容切分为可处理的块
5. LLM 为每个块生成幻灯片大纲（并行处理）
6. 合并所有大纲为统一结构
7. （可选）暂停等待人工审核
8. LLM 将大纲转换为 Marp Markdown
9. 图片 token 恢复为正确路径
10. Marp CLI 渲染为 PPTX/PDF/HTML

## 2.3 前后端分离架构

### 2.3.1 前端架构（React + TypeScript）

前端采用 React 18 + TypeScript + Next.js 构建：

**技术栈**:
- **React 18**: 组件化UI，Hooks 状态管理
- **TypeScript**: 类型安全，减少运行时错误
- **Next.js**: 服务端渲染，路由管理，API 代理
- **Tailwind CSS**: 原子化CSS，快速样式开发
- **Shadcn/ui**: 高质量UI组件库

**目录结构**:
```
frontend/src/
├── app/                    # Next.js App Router
│   ├── page.tsx           # 主页面
│   ├── layout.tsx         # 布局组件
│   └── globals.css        # 全局样式
├── components/            # React 组件
│   ├── UploadSection.tsx  # 文件上传
│   ├── TaskStatus.tsx     # 任务状态
│   ├── StepProgress.tsx   # 进度展示
│   ├── ResultSection.tsx  # 结果展示
│   ├── ResultEditor.tsx   # 结果编辑
│   └── ui/               # Shadcn UI 组件
└── lib/                   # 工具库
    ├── api.ts            # API 客户端
    └── utils.ts          # 通用工具
```

**核心功能模块**:

1. **文件上传模块**
   - 支持拖拽上传
   - 文件格式验证（仅 PDF）
   - 上传进度显示
   - 错误处理和重试

2. **任务监控模块**
   - 实时任务状态更新
   - 工作流进度可视化
   - 节点执行日志
   - 错误信息展示

3. **审核编辑模块**
   - 大纲内容展示
   - 在线编辑功能
   - 变更对比视图
   - 提交反馈按钮

4. **结果展示模块**
   - 演示文稿预览
   - 多格式下载
   - 结果历史记录
   - 分享功能

后端采用 Python 3.12 + FastAPI 构建：

**技术栈**:

**API 设计**:

FastAPI 提供以下主要端点：

| 端点 | 方法 | 功能 | 描述 |
|------|------|------|------|
| `/api/upload` | POST | 上传PDF | 接收并存储PDF文件 |
| `/api/tasks` | POST | 创建任务 | 启动新的转换任务 |
| `/api/tasks/{id}` | GET | 获取状态 | 查询任务执行状态 |
| `/api/tasks/{id}` | DELETE | 取消任务 | 中断正在执行的任务 |
| `/api/tasks/{id}/human-feedback` | POST | 提交反馈 | 人工审核后提交 |
| `/api/tasks/{id}/resume` | POST | 恢复任务 | 恢复暂停的任务 |
| `/api/tasks/{id}/markdown` | GET/POST | 获取/更新Markdown | 编辑中间结果 |
| `/api/download/{id}` | GET | 下载结果 | 下载生成的演示文稿 |
| `/api/render/preview` | POST | 预览渲染 | 实时预览Markdown |

**通信协议**:
- **前端 → 后端**: HTTP/JSON
- **后端 → LangGraph**: Python 函数调用
- **状态更新**: Server-Sent Events (SSE)

## 2.4 微服务划分

### 2.4.1 服务边界

ScholarFlow 采用**逻辑上的微服务架构**（非物理分离）：

**服务划分**:

1. **API 网关服务**
   - 职责: 请求路由、认证、限流
   - 技术: FastAPI
   - 端口: 8000

2. **工作流编排服务**
   - 职责: 业务逻辑编排、状态管理
   - 技术: LangGraph
   - 端口: 8123

3. **文档处理服务**
   - 职责: PDF 解析、文本提取
   - 技术: MinerU API
   - 外部依赖

4. **AI 处理服务**
   - 职责: LLM 调用、提示词管理
   - 技术: LangChain + OpenAI API
   - 外部依赖

5. **渲染服务**
   - 职责: Markdown 转演示文稿
   - 技术: Marp CLI
   - 外部依赖

6. **存储服务**
   - 职责: 状态持久化、文件存储
   - 技术: SQLite + JSON + 本地文件系统
   - 数据路径: `data/`

### 2.4.2 服务间通信

**同步通信**:
- HTTP/REST: API 调用
- 函数调用: 服务内部通信

**异步通信**:
- 事件驱动: 工作流节点间
- 回调: 外部服务通知

**数据同步**:
- 状态共享: 通过 WorkflowState
- 文件系统: 临时文件交换
- 数据库: 持久化存储

## 2.7 技术决策

### 2.7.1 为什么选择 LangGraph？

**对比方案**:
- Apache Airflow: 过于复杂，不适合我们的轻量级需求
- Celery: 仅提供任务队列，缺乏工作流抽象
- Temporal: 功能强大但学习曲线陡峭

**选择理由**:
- ✅ 专为 AI 应用设计，理解我们的需求
- ✅ 状态管理天然支持工作流场景
- ✅ 易于使用，API 设计优雅
- ✅ 活跃的社区和持续的更新

### 2.7.2 为什么选择 FastAPI？

**对比方案**:
- Django: 功能全但过于重量级
- Flask: 灵活但需要手动集成很多组件
- Tornado: 性能好但生态不够成熟

**选择理由**:
- ✅ 自动生成 API 文档
- ✅ 优秀的性能（基于 Starlette）
- ✅ 类型提示友好
- ✅ 现代化的异步支持

### 2.7.3 为什么选择 React？

**对比方案**:
- Vue.js: 同样优秀，但团队更熟悉 React
- Angular: 功能全面但学习曲线陡峭
- Svelte: 新兴框架，但生态不够成熟

**选择理由**:
- ✅ 丰富的生态系统
- ✅ 大量优秀的第三方库
- ✅ 优秀的开发工具支持
- ✅ 活跃的社区

### 2.7.4 存储方案决策

**对比方案**:
- 纯关系型数据库（PostgreSQL）: 过于复杂
- 纯文件系统: 缺乏事务支持
- NoSQL 数据库: 缺乏事务支持

**选择理由**:
- SQLite: 零配置、嵌入式、ACID 事务
- JSON: 人类可读、灵活、易调试
- 双存储: 结合两者优势
